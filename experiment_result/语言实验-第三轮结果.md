日期：2026-08-07 ｜ 模型：DeepSeek deepseek-chat ｜ 样本：3 臂 × 5 任务 × 10 = 150 ｜ 每样本最大轮数：5（全部 zero-shot + repair，few-shot 留 R3b）

原始数据：`logs/experiments/r3-binding-ab-2026-08-07T07-21-38-565Z/report.json`

## 实验设计

R2 剩下的主要摩擦是 `map` 的 `key="full_name"` 配置协议——模型想表达"对每个 repo 调用 `get_repository(repo.full_name)`"，却被要求"配置一个 MapNode"。R3 专测 **element→argument 数据绑定语法**：

> **H5（R3）：显式的数据流表达（`_.field → callable argument`）相比元数据式 binding（`key="field"`），能提高模型的 zero-shot binding correctness 与 repairability，而无需引入完整 lambda。**

三臂（syntax 是唯一变量，IR/runtime 一致）：

| 臂 | 绑定形态 | 哲学 |
|---|---|---|
| A | `map(repos, "github.get_repository", key="full_name")` | 配置 Map 节点（当前 DSL 基线） |
| B | `map(repos, github.get_repository(full_name=_.full_name))` | 描述数据怎么流入调用 |
| C | `map(repos, lambda repo: github.get_repository(full_name=repo.full_name))` | 描述一个真正的小程序（上限组） |

**5 个任务**覆盖 binding 难度梯度（防模型只记住 GitHub 固定模式）：

| 任务 | 源 → 工具 | binding 形态 |
|---|---|---|
| 1 repo-details | github.search → github.get_repository | 单字段同名（full_name→full_name） |
| 2 repo-languages | github.search → github.get_languages | 单字段同名 |
| 3 repo-contributors | github.search → github.list_contributors | 单字段同名 |
| 4 customer-detail | crm.search_customers → crm.get_customer | 单字段**异名**（id→customer_id） |
| 5 user-emails | users.list_users → email.prepare | **多字段**（email→to, name→name） |

指标分层：parse（首轮无 syntax 错误）/ conformance（first-attempt）/ execution（最终）/ task（沿 return 数据流 + binding 映射一致）/ **binding correctness（核心）**。

## 模型实际输出（关键证据）

1. **A 臂在异名任务写 `key="id"`，但工具参数叫 `customer_id`**：
   ```
   details = map(customers, "crm.get_customer", key="id")
   ```
   key= 语义是"参数名 == 字段名"，模型无从表达"把元素的 id 传给 customer_id"——被编译器以 unknown_parameter 拒绝，5 轮修复也绕不过（语言没有表达途径）。**命名映射缺失是 key= 的根本缺陷**。
2. **A 臂在多字段任务试图扩展 key=**：
   ```
   emails = map(users, "email.prepare", key="email", name="name")
   ```
   模型直觉地想给第二个参数也绑定字段（name="name"），但 map 只接受单一 key → unknown_parameter。**模型想表达多字段，语言不允许**——这正是 R3 设计假设（"key= 从根本上扩展性不足"）的直接实证。
3. **B 臂同任务一次写对**：
   ```
   details = map(customers, crm.get_customer(customer_id=_.id))
   emails = map(users.list_users(), email.prepare(to=_.email, name=_.name))
   ```
   `_.field → callable argument` 形态与模型的"对每个元素调用函数"心智模型完全对齐，异名/多字段天然可表达。
4. **B ≈ C**：两者 task/binding 均 100%，first-attempt 98%/96% 无实质差异。C 的唯一超额成本是引入 lambda 语法（lambda 关键字、局部参数、作用域）。

## 结论（H5 评估）

**H5 获强支持**：显式数据流绑定（B/C）相比元数据式 key=（A），binding correctness 从 60% 提到 100%，task 从 58% 提到 100%，且无需 lambda 即可达成。

1. **key= 只在"参数名==字段名"的平凡场景可用**（任务 1-3 接近 100%）；一旦出现命名差异（id→customer_id）或多字段（to/name），语言层面无表达途径 → 0%。**这是设计缺陷而非模型缺陷。**
2. **B 与 C 等效，选 B**：按实验预设决策规则（B≈C 则选 B），`_.field` 占位符调用在语言和编译器上都简单得多（无 lambda、无局部变量、无作用域），应进入候选语言。
3. **A 臂 first-attempt 52% 的二元分化**：同名任务首轮高、异名/多字段任务首轮也高（模型一次写对语法）但 task 全 0——模型语法没问题，是语义被语言能力卡死。
4. `_.` 单点占位符没有引入任何新摩擦（B 臂 error 几乎为零），模型能稳定写出 `_.field`。

**对语言设计的启示**：

1. **map 绑定应改为调用形态**：`map(source, tool(param=_.field, ...))`，支持多字段、支持参数名与字段名解耦。
2. **不引入 lambda**：B 臂已达上限，lambda 的复杂度（局部变量/作用域/编译器）没有带来额外收益。
3. **key= 可保留为退化兼容**（同名单字段快捷方式），但不再作为主协议。

## 方法论收获

1. **binding correctness 作为独立指标有效**：A 臂 execution 98% 但 task 58%——若只看执行成功率会严重高估；binding 检查（编译成功 + 映射与 spec 一致）抓住了"能跑但绑定错"的程序。
2. **任务多样性防止模式记忆**：5 个任务含异名/多字段，暴露了 key= 在简单任务上隐藏的缺陷——若只跑 GitHub 同名任务，R3 会误判"key= 没问题"。
3. **探针 + 修复循环组合依旧有效**：A 臂 unknown_parameter=21 记录了模型"想表达但语言不给"的挣扎，是设计缺陷的量化证据。
4. **harness 并发执行（--parallel）**：arm×task 组合并行（默认 6），150 样本运行时间大幅缩短，结果与串行一致。

## 下一步候选

2. **语言落地**：把 `map(source, tool(param=_.field))` 作为 map 的主语法进入 DSL（含编译器 IR bindings 已是产物），更新语法指南与工具目录渲染。
3. **R4 候选**：binding 表达定稿后，测数据流下游——`take/filter/sort` 的 element 级操作是否也需要类似调用形态（如 `filter(source, _.stars > 100)`），或转向 P4（真实 GitHub adapter）。

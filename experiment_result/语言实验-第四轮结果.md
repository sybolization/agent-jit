# 语言实验 第四轮：真实 GitHub Adapter + B 臂验证（mock → real）

日期：2026-08-07 ｜ 实验：`r3-binding-ab-2026-08-07T07-50-49-275Z`（backend=real）｜ 前置：R3（call 形态胜出）、传输协议（submit_program tool envelope）

## 目标

R3 用 mock GitHub 工具选出 B 臂（`map(source, tool(param=_.field))`）。R4 把 **mock 换成真实 GitHub REST API**（P4 adapter 的最小实现），用 B 臂 + 真实数据重跑 R3 的 5 个任务，验证：

> **真实数据下 B 臂仍保持高 conformance 与 binding correctness；DSL → IR → 真实 API → 执行的链路端到端成立；真实数据的字段/延迟/rate limit 不改变语言结论。**

## 实现

1. **真实 adapter**（`src/runtime/githubAdapter.ts`，新增）：4 个只读工具与 mock 同 spec，`fetch` + `Bearer GITHUB_TOKEN`，返回字段与 mock 对齐（full_name/stars/archived/language）；错误处理：429/403 rate limit（含 reset 时间）、404、15s 超时；`fetch` 可注入（测试不打真实 API）。
2. **harness `--backend=real|mock`**：默认 mock（实验可复现），R4 显式 real；任务 4/5 的 crm/email mock 域保留作对照。
3. **传输协议（同轮落地）**：模型通过 `submit_program(source)` tool call 提交程序，text 通道不参与解析——transport 指标与语法/编译解耦。
4. **测试**：`tests/githubAdapter.test.ts`（7 用例，mock fetch 验证 URL/header/字段映射/429/404/缺 token）。

## 关键发现与修复

1. **`%2F` 编码路径 404（真实 API 才暴露）**：初版把 `full_name`（owner/repo）整体 `encodeURIComponent` 后放 `/repos/{full_name}`，真实调用返回 404（mock 测不出——mock fetch 不校验 URL 语义）。修复：拆成 `/repos/{owner}/{repo}` 两段。**教训：URL 语义 bug 只能被真实端点暴露，mock 只能验证契约形状。**
2. **仓库重命名**：`facebook/react` 已被 GitHub 重定向为 `react/react`，adapter 返回服务端实际 `full_name`——不影响任务（binding 检查的是映射逻辑，不是仓库名）。
3. **网络直连可行**：api.github.com 直连成功，无需代理（与 git push 需代理的情况不同）。
4. **传输协议 50 样本 transport 100%**：submit_program tool envelope 下，模型 text 通道零污染，程序只从结构化 source 取。

## 结论与下一步

- **端到端成立**：DSL（call 形态）→ IR → 真实 GitHub API → 执行的链路在真实数据下 50/50 通过。
- **B 臂语言方向确认**：可进入"把 call 形态落地为 map 主语法"（去掉 `allowMapBinding` 开关的默认 false，或直接替换 key= 协议）。
- **P4 adapter 交付**：真实 GitHub 4 工具（REST V1，跳过 gh CLI V0）可作为 P5 agent node 的基础。
- 下一步候选：R3b（few-shot，示例不用 GitHub 域防泄漏）/ call 形态落地 DSL / P5 agent node。

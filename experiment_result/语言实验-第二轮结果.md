# 语言实验 第二轮：positional vs named 调用形态（2×2 factorial）

日期：2026-08-07 ｜ 模型：DeepSeek deepseek-chat ｜ 样本：4 臂 × 10 = 40 ｜ 任务：search → map → take → return（同一任务）｜ 每样本最大轮数：5

原始数据：`logs/experiments/positional-ab-2026-08-07T06-49-36-965Z/report.json`（修复后重跑）｜ `logs/experiments/positional-ab-2026-08-07T06-18-26-946Z/report.json`（修复前，仅 first-attempt 层可信）

> **勘误与重跑说明（2026-08-07 二轮审查后）**：初版实验的"repair loop 失效 / 第 2/3 轮空输出"是 **gateway 层 bug**（pi-ai 对 assistant 消息缺 `usage` 字段与 content 格式要求 → 多轮流式调用静默崩溃，`lazyStream` 把 error 当结果返回不抛异常），**不是模型行为**。修复（`src/llm/gateway.ts` 为 assistant 消息补 usage 并转 block 数组）后按计划参数（`--samples=10 --rounds=5`）重跑，拿到真实 repair 数据。**本报告以重跑数据为准；初版数据仅 first-attempt 层可信**（如下对比表）。另，`computeEffects` 的 main effect 算法曾少除以 2（已修复），本报告数值均为组均值差（单位 pp）。

## 实验设计

R1 的 friction 数据显示摩擦点不是 `tool="..."` 引号，而是 **function invocation shape**（map/take 位置参数、无括号 return、参数名幻觉）。R2 用 2×2 factorial 严格测这个假设：

> **H5：positional 调用形态（`map(repos, ...)` / `take(details, 3)` / `return top`）比 named（`map(source=..., ...)`）更贴合模型先验，能提升 conformance，且不与 few-shot 效应混淆。**

| 臂 | syntax | scaffolding | allowPositionalArgs | few-shot 示例 |
|---|---|---|---|---|
| A | named | zero-shot | false | 无 |
| B | named | few-shot | false | `map(source=repos, tool="...", key="full_name")` |
| C | positional | zero-shot | true | 无 |
| D | positional | few-shot | true | `map(repos, "github.get_repository", key="full_name")` / `return top` |

控制变量：tool 一律双引号字符串（R1 的裸标识符探针 `EXPECTED_STRING_GOT_CALLABLE_REF` 本实验 0 次触发）；任务、IR、runtime 完全不变。四层 metric：parse（首轮无 syntax 错误）/ conformance（first-attempt 编译成功）/ execution（最终编译+执行成功，含修复）/ task（`checkTaskCorrectness` 语义检查，沿 return 数据流路径）。

|---|---|---|---|

| 指标 | syntax effect（positional − named） | few-shot effect | interaction |
|---|---|---|---|
| parse | −0.15 | +0.45 | — |
| conformance（first-attempt） | +0.20 | +0.80 | −0.40 |
| task | +0.40 | +0.40 | — |

## 模型实际输出（关键证据）

1. **A 臂成功样本（第 2 轮修复）**：
   - round 1（positional，3 个 `POSITIONAL_ARG_NOT_ALLOWED`）：
     ```
     repos = map(search, tool="github.get_repository", key="full_name", concurrency=5)
     result = take(repos, count=3)
     return(result)
     ```
   - round 2（**一次改成完整 named**，成功）：
     ```
     repos = map(source=search, tool="github.get_repository", key="full_name", concurrency=5)
     result = take(source=repos, count=3)
     return(value=result)
     ```
   → 模型先验强，但**在诊断反馈下可一次纠正**（2/10 样本如此）。
2. **A 臂失败样本的"重复提交"失效模式（新发现）**：一个失败样本 round 2-4 **连续提交完全相同程序**（248 字符，卡在同一个 syntax 错误），round 5 才换输出但仍是 positional。修复轮次并非都有效——模型存在"不真正修改、原样重发"的行为，这是 repair 循环的真实摩擦点（初版被 gateway bug 掩盖）。
3. **C 臂 6 个修复成功样本集中在"补全 map"**：round 1 常见 `map(search, "github.get_repository", concurrency=5)`（漏 `key`）→ 反馈 `map 缺少必填参数 key` → 补上后成功。`undefined_reference=17` 大部分是 map 构建失败导致的级联。
4. **`map` 的 `key="full_name"` 配置协议持续摩擦**：模型写 `full_name="full_name"`（把工具参数名当 key）、`key=full_name`（当裸符号）、或漏掉 key。`take` / `return` 未表现出自身摩擦。
5. **B/D few-shot 四维 100% 且全部 first-attempt**：4 行示例后无论语法形态，模型一次写对、语义全对。

## 结论（H5 评估）

**H5 获强支持（修复后的最终指标）**：

1. **task 层面 positional 完胜：C 100% vs A 20%**（+0.40pp main effect）；conformance 也支持（C 40% vs A 0%，+0.20pp）。同 zero-shot 下，positional 语法让模型的能力从 20% 拉到 100%——差距远大于指令文本差异能解释的范围。
2. **A 臂的先验强度被精确刻画**：8/10 样本在 5 轮反馈下仍未改成 named（29 次 `POSITIONAL_ARG_NOT_ALLOWED`），但 2/10 一轮就改对——"模型把 map/take/return 当普通编程语言原语"的先验很强，**且可纠正性存在样本间差异**。
3. **repair 机制真实有效**（C 60% 靠修复），但存在"重复提交"失效模式（A 臂失败样本的典型死法）。
4. **few-shot 仍是最大杠杆**（conformance +0.80pp），B/D 双百证明示例可完全压过先验冲突；但 positional + zero-shot 的 C 臂 100% 说明语法形状本身也独立贡献了 +0.40pp（task）。
5. **prompt 不对称仍在**（A 臂 named 指南未显式展示完整调用形态），严格归因需 R2b；但 C 100% vs A 20% 的幅度使"指令显式度是主因"的解释力变弱。

**对语言设计的启示**：

1. LLM-first：**positional + few-shot 最优**（D 臂四维 100%），且 zero-shot 下 positional 也能到 100%（C 臂）——语法形状贴近模型先验是独立于示例的增益。
2. 若只能二选一：few-shot 优先（杠杆最大），但 positional 语法把 zero-shot 下限从 20% 提到 100%，二者不冲突、可叠加。
3. `map` 的 `key="..."` 配置协议是**新的主要摩擦源**（模型想表达"对每个 repo 调用 `get_repository(repo.full_name)`"）——R3 应转向 map data binding syntax。
4. 修复机制的工程启示：诊断反馈对多数样本有效，但需对"重复提交同一程序"做检测（连续 N 轮输出相同 → 视为 stuck，可强制注入示例或判负）。

## 方法论收获

1. **gateway 层 bug 会系统性扭曲修复层数据**：`pi-ai` 对 assistant 消息要求（a）`usage` 字段（`estimate.ts getLastAssistantUsageInfo` 读 `assistant.usage.totalTokens`），（b）content 为 block 数组（`estimateMessageTokens` 遍历 content 取 block 字段）。缺任一项，多轮对话静默崩溃、单轮无感。**教训：多轮修复类实验必须先验证"第二轮真的发出请求并拿到响应"，否则修复能力结论全是 bug 假象。**
2. **重跑的价值**：同参数下"50% → 100%"（C 臂）直接量化了 bug 对结论的污染幅度——修复前的 R2 结论（"反馈循环 0 挽回"）被彻底推翻。
3. **friction 探针 + 修复轮次组合**：既测"首轮先验"（first-attempt），又测"可纠正性"（repair 分布）——A 臂 2/10 可纠正、C 臂 6/10 靠修复，是两个独立维度的能力。
4. **task checker 沿数据流路径检查**（避免冗余节点 false negative）+ `queryTokens` 逐 token 检查（初版漏 `language:typescript` 判对）已修复。
5. **统计惯例**：2×2 main effect 用组均值差（÷2）并注明单位 pp。

## 下一步候选

1. **R2b：prompt 完全对称的 named vs positional**：named 臂也显式展示完整调用形态（含反例"不要写 map(repos, ...)"），把残余的指令显式度混淆拆掉。
2. **repair 循环增强**：检测"重复提交"（连续 2 轮输出相同 → 注入正确示例或判负），量化 stuck 对成功率的拖累。
3. **R3：map data binding syntax**：让模型表达"把 `repo.full_name` 传给 `github.get_repository`"，语义从"配置 MapNode"转向"描述对元素的调用"，同时保证编译器静态构图。

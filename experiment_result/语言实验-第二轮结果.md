# 语言实验 第二轮：positional vs named 调用形态（2×2 factorial）

日期：2026-08-07 ｜ 模型：DeepSeek deepseek-chat ｜ 样本：4 臂 × 10 = 40 ｜ 任务：search → map → take → return（同一任务）｜ 每样本最大轮数：3

原始数据：`logs/experiments/positional-ab-2026-08-07T06-18-26-946Z/report.json`

## 实验设计

R1 的 friction 数据显示摩擦点不是 `tool="..."` 引号，而是 **function invocation shape**（map/take 位置参数、无括号 return、参数名幻觉）。R2 用 2×2 factorial 严格测这个假设：

> **H5：positional 调用形态（`map(repos, ...)` / `take(details, 3)` / `return top`）比 named（`map(source=..., ...)`）更贴合模型先验，能提升 first-attempt conformance，且不与 few-shot 效应混淆。**

| 臂 | syntax | scaffolding | allowPositionalArgs | few-shot 示例 |
|---|---|---|---|---|
| A | named | zero-shot | false | 无 |
| B | named | few-shot | false | `map(source=repos, tool="...", key="full_name")` |
| C | positional | zero-shot | true | 无 |
| D | positional | few-shot | true | `map(repos, "github.get_repository", key="full_name")` / `return top` |

控制变量：tool 一律双引号字符串（R1 的裸标识符探针 `EXPECTED_STRING_GOT_CALLABLE_REF` 本实验 0 次触发，未被污染）；任务、IR、runtime 完全不变。四层 metric：parse（首轮无 syntax 错误）/ conformance（首轮编译成功）/ execution（最终编译+执行成功）/ task（`checkTaskCorrectness` 语义检查，与执行解耦）。

> 说明：本实验 `--rounds=3`（计划书写 `rounds=5`）。收敛依据：失败样本第 2/3 轮多为空输出（见下文发现 2），多给轮数无增量信息，同时省去 20 次 API 调用。如需复核可重跑 `--rounds=5`。

|---|---|---|---|

## 模型实际输出（超出假设的发现）

1. **A 臂 31 次 `POSITIONAL_ARG_NOT_ALLOWED`：named 语法与模型先验的冲突被探针直接量化**。语法指南明确写了"map：source 必须是先前定义的数组变量"，但 10/10 样本首轮仍写 `map(search, tool="...", key="full_name")`——第一个参数照旧位置化。被拒绝后第 2/3 轮**输出为空**（10/10 样本），模型既不改成 named，也不解释，直接放弃。
2. **反馈循环本实验 0 次成功挽回**：所有成功样本（B/D 20 个 + C 5 个）全部是 first-attempt；失败样本没有任何一个通过诊断反馈在第 2/3 轮修复。zero-shot 臂收到编译诊断后的典型行为是**空输出**（A 10/10，C 部分样本）——feedback loop 当前只对"会改"的模型有用，而 zero-shot 模型不会改。
3. **C 臂失败的 root error 是"缺参数"，`undefined_reference` 是级联噪音**。例：`map(search, "github.get_repository", concurrency=5)` 漏了 `key` → map 构建失败 → 后续 `take(details)` / `return top` 全部报"引用了未定义的变量"。10 次 undefined_reference 中大部分是这种级联，真正的独立错误只有 4 次 syntax + 3 次 unknown_parameter。
4. **few-shot 臂（B/D）四维 100% 且全部 first-attempt**：给 4 行示例后，无论 named 还是 positional，模型一次写对、语义全对。示例即一切。

## 结论（H5 评估）

**H5 部分获支持。** 分层看：

- **conformance：positional 更贴先验（+0.50）**。同 zero-shot 下 C=50% vs A=0%——C 的 5 个成功全是"模型自主写的位置参数形态恰好被语言接受"（无任何示例）；而 A 的 0% 纯粹是探针拒绝（模型先验是 positional，强行要求 named 则归零）。
- **parse：positional 反而更差（−0.40）**。`return top` 无括号、位置参数与命名混用等新形态给语法层带来新错误空间。
- **few-shot 仍是最大杠杆（conformance +1.50 / task +1.60）**，且 B 臂证明 **named + few-shot 同样 100%**——语法形状不是决定性的，示例才是。

**对语言设计的启示**：

1. 若目标是 LLM-first：**positional + few-shot 是最优组合**（D 臂，四维 100%），且位置参数形态正是模型自发先验，摩擦最小。
2. 若只能二选一：**few-shot（示例）优先于语法形状**——B/D 双百证明示例可以完全压过先验冲突。
3. named 语法不必须移除，但保留它就必须用 few-shot 兜底；**zero-shot 用户直接给 named 指南会 0% 崩盘**（A 臂数据是这条的语言设计证据）。

## 方法论收获

- **friction 探针方法论在 2×2 下威力更大**：A 臂"0% + 31 次同错误码 + 空输出"是把"named 语法 vs 模型先验冲突"从 anecdote 变成可量化证据——探针不是 error，是测量仪器。
- **四层 metric 分层有效**：A 臂 parse 100% / conformance 0% 精确区分"语法层完全没问题，语义层被语言拒绝"——若只看 execution 或 parse 都会误判失败原因。
- **task_correctness 与执行解耦的价值**：C 臂 execution 50% 但 task 40%——2 个样本执行成功但程序没完成任务要求（如 query 不含关键词），单看 execution 会高估能力。
- 反馈循环的无效性（发现 2）提示下一轮实验设计应考虑：失败后是"继续反馈"还是"直接判负"——当前数据支持后者更省 token 且不漏信息。

## 下一步候选

2. 或 **feedback 循环干预实验**：空输出时注入更明确的纠正示例（few-shot 动态注入），测能否救回 zero-shot 失败样本。
3. 或 **直接推进 P4（GitHub adapter）**：语言形状问题已基本收敛（positional+fs = 100%），R2 结论可先落进语法指南，把实验预算转向真实工具链路。

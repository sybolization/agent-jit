我建议 R3 不要再研究“named vs positional”了，而是专门研究一个更窄的问题：

> **当 `map` 需要把列表里的每一项，传给另一个工具时，哪种表达方式最符合模型直觉，同时又最容易被编译器静态理解？**

这正是 R2 剩下的主要摩擦点。

比如当前写法：

```text
details = map(
    repos,
    "github.get_repository",
    key="full_name"
)
```

人类能理解它的意思是：

> 对 `repos` 里的每一个 repo，取出 `repo.full_name`，然后调用 `github.get_repository(full_name=...)`。

但这个含义其实被拆成了三个元数据：

```text
repos
"工具名"
key="full_name"
```

模型并没有直接看到：

```text
repo.full_name → github.get_repository(...)
```

所以 R3 就应该研究：**怎样把这条“数据连线”表达得更自然。**

---

## 我建议 R3 先做 3 臂，而不是 2×2

先不要加入 few-shot。

因为 R2 已经证明了一个事实：

> 给足够接近答案的 few-shot，几乎什么语法都能做到 100%。

R3 更应该观察模型的**自然生成倾向**。

所以第一阶段全部 zero-shot + compiler repair。

### A：当前 `key=` 基线

```text
details = map(
    repos,
    "github.get_repository",
    key="full_name"
)
```

它代表你现在的 DSL。

---

### B：占位符表达式

我很建议测试这个：

```text
details = map(
    repos,
    github.get_repository(full_name=_.full_name)
)
```

这里 `_` 表示：

> 当前正在处理的那个元素。

如果当前元素是 repo：

```text
_.full_name
```

就是：

```text
repo.full_name
```

它非常接近模型熟悉的代码表达，但没有引入 lambda。

Compiler 也很好分析：

```text
_
↓
当前 map element
↓
.full_name
↓
传入 github.get_repository.full_name
```

它仍然能静态编译成：

```text
MapNode
 source = repos
 callable = github.get_repository
 binding:
   full_name ← element.full_name
```

我觉得这是非常值得测的一种设计。

---

### C：Lambda / Python-shaped

例如：

```python
details = map(
    repos,
    lambda repo: github.get_repository(
        full_name=repo.full_name
    )
)
```

这是最接近 Python 训练先验的方案。

它非常直观：

> 对每一个 repo，调用这个函数。

但语言复杂度明显增加了。

因为你开始需要：

```text
lambda
局部变量 repo
attribute access
expression scope
call expression
```

所以 C 更像一个“上限组”。

如果 C 明显比 B 好很多，那么 lambda 的复杂度可能值得。

如果：

```text
B ≈ C
```

那就应该选择 B，因为 B 的语言和编译器都简单得多。

---

# 三组其实代表三种哲学

A：

```text
map(repos, tool, key="full_name")
```

是在说：

> **配置一个 Map 节点。**

B：

```text
map(repos, tool(full_name=_.full_name))
```

是在说：

> **描述数据怎么流入调用。**

C：

```text
map(repos, lambda repo: tool(repo.full_name))
```

是在说：

> **描述一个真正的小程序。**

所以 R3 不只是测试几个符号。

它实际是在回答：

> Agent DSL 应该偏“图配置语言”，还是偏“受限的程序语言”？

---

## 我特别建议不要只用一个 GitHub 任务

否则模型可能只是学会：

```text
full_name
```

这个固定模式。

R3 应该设计 4～6 个非常小的任务，而且要求的 binding 不一样。

例如 GitHub 可以有：

```text
RepositorySummary.full_name
→ github.get_repository(full_name=...)
```

```text
Repository.full_name
→ github.get_languages(full_name=...)
```

```text
Repository.full_name
→ github.list_contributors(full_name=...)
```

再加几个 mock tool：

```text
Customer.id
→ crm.get_customer(customer_id=...)
```

```text
Order.user_id
→ users.get_user(id=...)
```

```text
File.path
→ filesystem.read(path=...)
```

这样才能知道：

> 这个语法是真的让模型理解了“element → argument binding”，

而不是：

> 模型只记住了 GitHub 的 `full_name`。

---

# 还应该有一个稍微难一点的 binding

最简单的都是：

```text
一个字段 → 一个参数
```

但真实 agent 很快会遇到：

```text
一个元素的多个字段 → 多个工具参数
```

例如：

```text
user.email
user.name
```

传给：

```text
email.send(
    to=user.email,
    subject=...
)
```

所以可以设置一类任务：

```text
records = map(
    users,
    ...
)
```

目标调用需要两个字段。

A 的 `key=` 方案在这里马上开始变难，因为一个：

```text
key="..."
```

已经不够表达多个参数了。

而 B：

```text
map(
    users,
    email.prepare(
        to=_.email,
        name=_.name
    )
)
```

天然可以表达。

C：

```python
map(
    users,
    lambda user: email.prepare(
        to=user.email,
        name=user.name
    )
)
```

也天然支持。

这会帮助你判断：

> 当前 `key=` 设计是不是从根本上扩展性不足。

我其实已经比较怀疑它是。

# R3 最重要的指标

我会保留 R2 的指标，但增加一个专门指标：

**binding correctness**。

也就是专门检查：

> 模型有没有把正确的 element field 接到正确的 tool parameter。

例如：

```text
repo.full_name
↓
github.get_repository.full_name
```

不能只是程序编译成功。

因为模型可能写：

```text
repo.name
```

也可能正常执行，但语义是错的。

所以指标大概是：

* first-attempt compile conformance
* first-attempt task correctness
* binding correctness
* repair conversion rate
* average repair rounds
* tokens per successful task
* error distribution

其中我会把：

```text
binding correctness
```

作为 R3 的核心指标。

# Repair 这次一定保留

因为 R2 已经证明 Repairability 非常有区分度。

比如可能出现：

```text
A
首轮 40%
repair 后 70%

B
首轮 60%
repair 后 100%

C
首轮 70%
repair 后 100%
```

那 B 很可能就是甜蜜点。

因为 C 虽然第一次多 10%，却要求整个语言加入 lambda。

工程上未必值得。

---

# 我建议样本数提高

R2 每臂 10 次适合探索。

R3 已经开始决定语言设计了，我建议至少：

```text
3 syntax arms
×
5 tasks
×
10 generations
```

也就是每臂：

```text
50 个样本
```

总共 150 次。

这样还能看：

```text
不同 task 下是否稳定
```

而不只是总成功率。

如果成本高，可以先：

```text
3 × 5 × 5 = 75
```

作为 R3a。

发现明显差异之后再扩大。

## Few-shot 放到 R3b

R3a 先：

```text
A/B/C
全部 zero-shot
+
repair
```

回答：

> 模型天然喜欢什么？

然后如果 B/C 真的表现不错，再做 R3b：

```text
最佳候选语法
×
zero-shot / generic few-shot
```

注意这个 few-shot 一定不要使用 GitHub。

例如实验任务是 GitHub，示例用：

```text
customers → crm.get_customer
```

这样 few-shot 只教：

> 语法。

而不是把任务答案骨架也教给模型。

# 我个人最期待 B

如果现在让我下注，我不会直接押 lambda。

我更想看看这种语法：

```text
repos = github.search_repositories(
    query="agent framework language:typescript",
    limit=10
)

details = map(
    repos,
    github.get_repository(
        full_name=_.full_name
    )
)

top = take(details, 3)

return top
```

因为它同时具备几个特点：

```text
非常像代码
+
模型应该容易理解
+
没有 lambda
+
没有任意循环
+
没有局部函数
+
编译器仍然可以完全静态分析
+
天然支持多个参数 binding
```

甚至以后：

```text
messages = map(
    users,
    email.prepare(
        to=_.email,
        name=_.name
    )
)
```

都可以自然表达。

它可能正好落在：

```text
JSON/config DSL
        ←──── B ────→
                  Python
```

中间那个你一直在找的平衡点。

所以我会把 R3 的核心 hypothesis 写成：

> **H5：显式的数据流表达（`_.field → callable argument`）相比元数据式 binding（`key="field"`），能提高模型的 zero-shot binding correctness 与 compiler-guided repairability，而无需引入完整 lambda/control-flow semantics。**

如果 B 能接近 C，同时明显超过 A，那这一轮很可能会确定你这门语言一个非常核心的语法方向。

我会建议 R4 **暂时离开语法实验，回到系统级假设**。

R1–R3 已经逐步回答了：

```text
R1  callable 怎么表达？
R2  控制原语应该长什么样？
R3  map 里的数据绑定怎么表达？
```

如果 `submit_program(source=...)` 也已经把传输层固定下来，那么下一步最有价值的问题是：

> **这门语言到底能不能让 Agent 执行复杂工具任务时，比传统逐步 Tool Calling 更高效、更可靠？**

也就是回到这个项目最初的大命题。

## 我会把 R4 定义成：Programmatic Tool Calling Benchmark

比较两种架构。

### A：传统 Tool Calling

模型：

```text
LLM
 ↓
search_repositories
 ↓
LLM 看结果
 ↓
get_repository(A)
 ↓
LLM
 ↓
get_repository(B)
 ↓
LLM
 ...
 ↓
最终回答
```

每一步模型决定下一步调用。

### B：DSL Program

模型一次：

```text
LLM
 ↓
submit_program(source="...")
 ↓
Compiler
 ↓
Runtime
 ↓
search → map × N → filter → take
 ↓
必要时最后再回 LLM
```

模型不再位于每条数据边上。

这才是你项目真正的大价值验证。

---

# R4 最重要的自变量：任务复杂度

不要只设计一个任务。

我会固定任务语义，然后改变工具调用规模：

```text
Small    5 次左右工具调用
Medium  10 次
Large   20 次
XL      40 次
```

例如 GitHub：

```text
search repos
   ↓
N × get_repository
   ↓
N × get_languages
   ↓
filter
   ↓
take
   ↓
return
```

分别令：

```text
N = 2 / 5 / 10 / 20
```

你真正想画出来的是两条曲线：

```text
成本
 ^
 |                 traditional
 |              /
 |           /
 |        /
 |     /
 |  DSL
 | /
 +--------------------> task complexity
```

如果传统 Tool Calling 随着工具节点增加迅速膨胀，而 DSL 接近线性甚至趋平，那么这个结果会非常强。

---

# 我最想看的不是“快几倍”

而是这几个指标随复杂度怎么增长。

### 1. LLM round trips

这可能是 R4 最直观的指标。

传统：

```text
5 tools  → 可能 6 次模型调用
20 tools → 可能 21 次
40 tools → 可能更多
```

DSL：

```text
5 tools  → 1~2 次
20 tools → 1~2 次
40 tools → 1~2 次
```

如果成立，这实际上在证明：

> **复杂度被从 token loop 转移到了 deterministic runtime。**

---

### 2. Intermediate data exposed to LLM

这个指标我非常建议第一次正式加入。

假设：

```text
search 返回 20 repos
20 × get_repository
20 × get_languages
```

中间产生：

```text
300 KB
```

传统 Agent 可能大量数据都会进入 context。

DSL runtime 可以在本地：

```text
filter
project
take
```

最后只把：

```text
8 KB
```

送给 LLM。

可以定义：

```text
model_exposed_bytes
```

或者：

```text
model_exposed_tokens
```

这个指标非常能说明为什么 programmatic tool calling 有意义。

---

### 3. Total tokens

继续保留：

```text
input
output
cacheRead
total
```

尤其要看：

```text
tokens / successful task
```

因为失败任务不能当成低成本任务。

---

### 4. End-to-end latency

不是单独：

```text
LLM latency
```

而是：

```text
用户请求
↓
任务真正完成
```

包括：

* 模型生成
* compiler repair
* tool calls
* parallel runtime
* final synthesis

真正产品关心的是这个。

---

### 5. Successful task completion

不要只测：

```text
compile success
```

R3 已经证明：

> 可执行 ≠ 语义正确。

所以 R4 一定继续：

```text
transport_success
compile_success
execution_success
task_correctness
```

最终最重要：

```text
completed_task_rate
```

---

# R4 最好同时做 Mock 和 Real 两层

这一点很重要。

如果全用 GitHub：

```text
网络抖动
rate limit
API latency
GitHub 服务状态
```

都会污染结果。

所以先做：

### R4a：Deterministic Mock

工具固定：

```text
latency = 50 ms
固定输入
固定输出
无网络失败
```

这样测的是纯架构：

```text
LLM loop vs DSL runtime
```

然后：

### R4b：Real GitHub

换成真实 API。

证明：

> 这种优势不仅存在于实验环境，也能落到真实外部工具。

两层结果一起非常有说服力。

---

# 任务不要只测试 fan-out

我会准备三个 workload。

### Workload 1：Fan-out

```text
search
 ↓
N × get_repository
 ↓
take
```

测并发和 scaling。

### Workload 2：Fan-out + transformation

```text
search
 ↓
N × get_repository
 ↓
N × get_languages
 ↓
filter
 ↓
sort
 ↓
take
```

测中间数据是否需要经过 LLM。

### Workload 3：Fan-out + semantic node

```text
search
 ↓
get details × N
 ↓
deterministic filter
 ↓
agent.rank(...)
 ↓
return
```

这里非常重要。

因为你不是要消灭 LLM。

而是要证明：

> **LLM 只出现在真正需要语义计算的位置。**

架构变成：

```text
Tool
 ↓
Tool
 ↓
Compute
 ↓
LLM semantic node
 ↓
Return
```

而不是：

```text
Tool → LLM → Tool → LLM → Compute → LLM
```

这正是你的核心思想。

# 我甚至会把 R4 的核心 Hypothesis 写得很简单

**H6：**

> As tool-graph complexity increases, programmatic DSL execution reduces LLM round trips, model-exposed intermediate data, token consumption, and end-to-end latency relative to iterative tool calling, without reducing task correctness.

中文：

> **随着工具图复杂度增加，DSL 编程执行相较逐步 Tool Calling，应显著降低模型调用次数、中间数据暴露、token 和端到端延迟，同时保持任务正确率。**

这个假设如果成立，项目的价值就从：

> “LLM 更容易写这种 DSL”

升级成：

> **“这种执行架构比现有 Agent Tool Calling 范式更有效。”**

这是大很多的一步。

## 我暂时不会在 R4 做 Multi-Agent

虽然非常诱人。

因为：

```text
Agent node
Program node
Tool node
```

同时调度正是你最终想去的地方。

但 multi-agent 会带入：

* Agent prompt
* 不同角色
* LLM variance
* 上下文共享
* semantic quality
* termination

会让 R4 变脏。

我会把它留给 R5。

R4 先把：

> **单 Agent + 多 Tool program**

这个系统级结论钉死。

然后 R5 很自然：

```text
Tool Node
Compute Node
Agent Node
```

统一调度。

---

```text
R3.5 / Transport

R4

```

> **DSL 不仅是更适合 LLM 的语言，它还能改变 Agent 执行工具的基本方式。**

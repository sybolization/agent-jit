这一轮实验可以理解成：**我们不再只问“模型第一次会不会写对 DSL”，而是开始问“这个语言在模型写错以后，好不好修”。**

这其实非常重要，因为真正的 Agent 系统里，LLM 不可能永远一次写对。一个好的 DSL 应该满足两件事：

1. 模型天然容易写。
2. 就算写错，编译器告诉它哪里错之后，它能快速修正。

所以这一轮 R2 的目的，是同时测这两个维度。

---

## 先说实验任务

所有实验组做的是同一个 GitHub 任务，大意是：

> 搜索 TypeScript 的 agent framework 仓库，拿到若干仓库信息，进一步调用 `github.get_repository` 获取详情，然后取前 3 个结果并返回。

逻辑结构始终一样：

```text
GitHub 搜索
   ↓
对搜索结果逐个 get_repository
   ↓
取前 3 个
   ↓
返回
```

底层 Execution IR 和 Runtime 也是一样的。

也就是说，我们不是在比较不同算法，只是在比较：

> **同一件事，用哪种 DSL 表面语法让 LLM 来写比较容易。**

---

# 第一种语言：Named / 配置式写法

这是你最初的设计：

```text
repos = github.search_repositories(
    query="agent framework language:typescript",
    limit=10
)

details = map(
    source=repos,
    tool="github.get_repository",
    key="full_name",
    concurrency=5
)

top = take(
    source=details,
    count=3
)

return(
    value=top
)
```

特点是：

> 每一个参数都写清楚名字。

比如：

```text
source=repos
count=3
value=top
```

这种写法对编译器特别友好，因为每个东西是什么意思都非常明确。

但我们怀疑它不一定对模型友好。

---

# 第二种语言：Positional / Python-shaped 写法

另一种写法是：

```text
repos = github.search_repositories(
    query="agent framework language:typescript",
    limit=10
)

details = map(
    repos,
    "github.get_repository",
    key="full_name",
    concurrency=5
)

top = take(details, 3)

return top
```

这里最大的变化是：

```text
map(source=repos, ...)
```

变成：

```text
map(repos, ...)
```

以及：

```text
take(source=details, count=3)
```

变成：

```text
take(details, 3)
```

以及：

```text
return(value=top)
```

变成：

```text
return top
```

这明显更像 Python 或其他普通编程语言。

---

# 然后每种语言又分成两个条件

一个是：

> **Zero-shot**

意思是不给模型完整范例，只告诉它规则，让它自己写。

另一个是：

> **Few-shot**

给它一个完整示例，让它照着学习这个语言怎么写。

所以最后有四组：

| 组 | 语法         | 是否给示例 |
| - | ---------- | ----- |
| A | Named      | 不给    |
| B | Named      | 给     |
| C | Positional | 不给    |
| D | Positional | 给     |

也就是一个 2×2 实验。

目的就是把两个因素拆开：

```text
因素 1：语言本身自然不自然？
因素 2：给示例能不能补偿语言的不自然？
```

---

# 这一轮新加入的核心：Repair

以前模型第一轮写错以后，理论上系统会：

```text
模型写 DSL
   ↓
Compiler 检查
   ↓
发现错误
   ↓
把错误信息告诉模型
   ↓
模型重新修改 DSL
```

比如模型写：

```text
take(details, 3)
```

但当前实验组要求：

```text
take(source=details, count=3)
```

Compiler 会告诉它：

```text
位置参数不允许
```

模型就应该第二轮改成正确写法。

这就是：

> **compiler-guided repair**

上一轮这个 repair loop 有 bug，所以模型失败后没有真正有效修改。

这一轮你把它修好了。

于是这次第一次真正测到了：

> **不同语言的可修复性。**

---

# 为什么“可修复性”非常重要？

假设有两种语言。

语言甲：

```text
第一次写对率：40%
```

看起来不高。

但剩下 60%：

```text
编译器告诉模型错误
↓
模型第二轮全部修好
```

最终：

```text
100% 完成任务
```

这是非常好的 Agent language。

而语言乙：

```text
第一次写对率：60%
```

似乎更高。

但剩余 40%：

```text
改一次
还是错

改两次
还是错

改五次
还是错
```

那么真正放到生产里，语言乙可能反而更差。

因为会产生大量：

* LLM 调用
* token
* latency
* repair context
* 失败任务

所以这一轮的实验目的已经从：

> “语法准确率”

升级成：

> **“LLM 与编译器能不能围绕这种语言稳定收敛。”**

---

# 实验结果

这次最关键的是：

| 组                        | 第一次写对 | Repair 后最终成功 |
| ------------------------ | ----: | -----------: |
| A Named / zero-shot      |  0/10 |     **2/10** |
| B Named / few-shot       | 10/10 |    **10/10** |
| C Positional / zero-shot |  4/10 |    **10/10** |
| D Positional / few-shot  | 10/10 |    **10/10** |

最值得看的不是 B 和 D。

因为 B/D 都给了示例，模型基本可以模仿答案。

真正值得比较的是：

```text
A vs C
```

两者都没有示例。

区别只是语言形状。

---

# A：Named zero-shot 发生了什么？

第一次：

```text
0 / 10
```

没有一次完全符合语言。

这意味着在没有示例的时候，模型几乎不自然地产生：

```text
take(source=x, count=3)
return(value=x)
```

它更喜欢：

```text
take(x, 3)
return x
```

这正是我们前面发现的“Python 形状先验”。

但是这次 repair 开始工作以后，更有意思。

10 个失败任务里，最终只修回来：

```text
2 / 10
```

也就是说：

> Compiler 已经明确告诉模型哪里错，但模型仍然很难持续服从 Named 语法。

尤其是：

```text
return(value=result)
```

这里问题非常明显。

模型会不断尝试：

```text
return result
```

甚至被告知错误以后还会写：

```text
return value=result
```

它在努力“折中”：

```text
我知道你需要 value=result
但 return 在我的程序语言知识里应该是 statement
```

于是产生一个两边都不像的：

```text
return value=result
```

这很有意思。

说明这里不是普通的“模型忘记规则”。

而是：

> **DSL 规则正在和模型极强的编程语言先验发生冲突。**

---

# C：Positional zero-shot 发生了什么？

第一次：

```text
4 / 10
```

直接正确。

第一次成功率当然还不算高。

但关键来了。

剩下：

```text
6 个失败
```

经过 Compiler feedback：

```text
6 个全部修正
```

最终：

```text
10 / 10
```

这是这一轮最重要的数据。

---

# 为什么 Positional 更容易修？

因为它剩下的错误通常非常局部。

例如模型写：

```text
map(
    repos,
    "github.get_repository"
)
```

Compiler 说：

```text
缺少 key
```

模型马上知道：

```text
哦，加：

key="full_name"
```

就行。

或者它写：

```text
key=full_name
```

Compiler 说：

```text
key 需要字符串 literal
```

模型修改成：

```text
key="full_name"
```

成功。

这些都是：

> **局部、明确的小错误。**

模型不需要改变它对整个程序结构的理解。

---

# 而 Named 的错误更像“结构冲突”

比如 Compiler 告诉模型：

```text
return 必须写：
return(value=result)
```

但模型脑子里的大量训练数据都在说：

```python
return result
```

所以这不是：

> “漏了一个引号。”

而是：

> “你要求我改变我理解 `return` 这个东西的方式。”

这种错误明显更难 repair。

---

# 所以这一轮真正想回答的问题是什么？

其实是三个问题。

### 第一：模型天然喜欢哪种写法？

答案目前明显偏：

```text
Positional / Python-shaped
```

尤其：

```text
take(x, 3)
return x
```

模型非常自然。

---

### 第二：如果语言不自然，few-shot 能不能解决？

答案是：

> 可以。

B：

```text
Named + few-shot = 10/10
```

说明只要把正确示例放进 prompt，模型完全有能力使用 Named DSL。

所以 Named 不是“模型学不会”。

它只是：

> **需要额外教学。**

---

### 第三：如果不靠 few-shot，只靠 Compiler feedback 呢？

这是这次最重要的实验。

结果：

```text
Named:
0/10 → 2/10

Positional:
4/10 → 10/10
```

所以：

> **Positional 语言显著更容易和 compiler 形成 repair loop。**

---

# 这对 Agent DSL 有非常现实的意义

你的最终系统可能是：

```text
用户
 ↓
LLM
 ↓
生成 DSL
 ↓
Compiler
 ↓
如果错误
 ↓
Diagnostic
 ↓
LLM 修复
 ↓
ExecutionIR
 ↓
Runtime
```

所以真正重要的并不是：

```text
LLM 第一次必须 100% 正确
```

而是：

```text
LLM + Compiler
是否能够快速收敛到正确程序
```

这是一个很不同的语言设计目标。

传统编程语言主要为：

> 人写代码。

你的 DSL 是为：

> LLM + Compiler 协同写程序。

所以可以定义一个新的语言质量指标：

```text
生成成功率
+
Repairability
+
Repair cost
```

---

# 这一轮也开始告诉我们：语言里不是所有东西都需要 Python 化

这个结论也很重要。

比如工具本身：

```text
github.search_repositories(
    query="...",
    limit=10
)
```

模型没有什么问题。

这种 named argument 非常合理。

因为：

```text
query
limit
```

都是业务含义。

但是：

```text
return(value=x)
```

明显是不自然的。

所以最终的语言可能不是：

> 全部 Python。

也不是：

> 全部配置 DSL。

而是混合：

```text
工具调用：
named arguments

github.search_repositories(
    query="...",
    limit=10
)

语言原语：
Python-shaped

take(items, 3)

return items
```

这其实越来越像一个合理的设计边界。

---

# 这一轮还暴露出了下一步研究对象：`map`

`take` 和 `return` 的方向现在已经比较清楚。

剩下最麻烦的是：

```text
map(
    repos,
    "github.get_repository",
    key="full_name"
)
```

这里模型经常不理解：

```text
key="full_name"
```

到底是什么。

因为模型真正想表达的是：

> 对每一个 repo，调用：

```text
github.get_repository(repo.full_name)
```

而我们现在却要求它把这个含义拆成：

```text
source = repos
tool = github.get_repository
key = full_name
```

所以 R2 的任务基本完成了。

下一轮 R3 应该研究的是：

> **怎么表达 map 内部的数据绑定最符合模型习惯？**

比如可能测试：

```text
map(
    repos,
    "github.get_repository",
    key="full_name"
)
```

对比某种更程序化的：

```text
map(
    repos,
    repo => github.get_repository(repo.full_name)
)
```

不一定最后采用 lambda，只是实验这个语义形状。

---

## 最后把这一轮目的压缩成一句话

R1 问的是：

> “工具名要不要写得像 Python？”

R2 问的是：

> **“语言的控制结构要不要写得像模型已经熟悉的程序？”**

Repair 修复后的 R2 又进一步回答：

> **Python-shaped control syntax 不只让模型更容易第一次写对，也让 Compiler 更容易把错误程序修到正确。**

这就是这一轮实验真正的内容与目的。

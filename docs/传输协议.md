我赞成，而且我认为这不是退回“工具调用方案”，而是把**传输协议**和**程序表达语言**分开。

你现在遇到的 2.7% 污染，本质上很可能是这个问题：

````text
LLM
 ↓
自由文本 channel
 ↓
“这里是代码：”
```dsl
...
````

↓
程序性剥 Markdown
↓
Parser

````

这条链路的问题不是 DSL 本身，而是：

> **你让模型通过一个允许自然语言的自由文本通道提交机器可执行程序。**

如果落地，确实不应该长期依赖：

```text
stripCodeFence()
stripMarkdown()
extractFirstCodeBlock()
````

这属于 heuristic transport parsing。模型输出稍微变化一下：

```text
Here is the program:
...
Hope this helps.
```

或者多一个解释段，就需要不断加规则。

更稳的架构应该是：

```text
LLM
 ↓
结构化 tool call
 ↓
submit_program(source: string)
 ↓
DSL Compiler
 ↓
ExecutionIR
 ↓
Runtime
```

例如模型最终不是直接输出：

```text
repos = ...
details = ...
return top
```

而是调用一个唯一工具：

```text
submit_program(
    source="repos = ...\ndetails = ...\nreturn top"
)
```

这里 **tool calling 只是 envelope**。

真正的 computation 仍然由你的 DSL 表达。

---

## 这和传统 Tool Calling 完全不是一回事

传统模式是：

```text
LLM
→ github.search
→ LLM
→ github.get_repository
→ LLM
→ github.get_repository
→ ...
```

你想做的依然是：

```text
LLM
→ submit_program(
     """
     repos = github.search(...)
     details = map(...)
     top = take(...)
     return top
     """
   )
→ Harness 执行整个程序
```

所以模型依然只推理一次，Runtime 依然掌握：

* 并行
* 数据流
* tool orchestration
* agent orchestration
* retry
* execution graph

只是最后的“交卷动作”通过结构化调用完成。

我甚至认为这是更干净的系统分层。

---

# 可以把系统明确拆成三层

### 第一层：Transport

解决：

> 模型怎么可靠地把东西交给 Harness？

这里用 function/tool calling：

```text
submit_program
```

这个层面应该尽可能 boring、可靠、结构化。

### 第二层：Language

解决：

> 模型怎么表达一个复杂的 Agent computation？

这里是你的 DSL：

```text
search
map
agent
take
return
...
```

### 第三层：Execution

解决：

> 这个程序怎么真正运行？

这里是：

```text
Compiler → IR → Scheduler → Runtime
```

也就是说：

```text
Tool Calling ≠ Agent Language

Tool Calling = Transport Protocol
DSL          = Program Representation
ExecutionIR  = Runtime Representation
```

我觉得这个区分非常重要。

---

# 为什么这个设计比 Markdown stripping 健壮

假设要求模型直接输出代码。

你实际上需要处理：

```text
纯代码
```

````text
```dsl
纯代码
````

````

```text
下面是程序：

```dsl
...
````

````

```text
我认为可以这样：

...
````

甚至：

```text
Program:
...

Explanation:
...
```

你只能不断猜：

> 哪部分才是 source？

而使用 tool call 后，Harness 根本不关心 assistant text。

它只接受：

```text
submit_program.source
```

于是 contract 非常明确：

```text
source 必须是一段 DSL source string
```

模型即使另外说了一段自然语言：

```text
“我已经生成好了。”
```

也不会污染程序。

# 更重要的是：这会改善 compiler repair

现在 repair 大概是：

```text
LLM 输出文本
↓
尝试抽代码
↓
Compiler
↓
diagnostics
↓
重新 prompt
```

改成 tool envelope 后：

```text
submit_program(source=...)
        ↓
      Compiler
        ↓
diagnostics
        ↓
LLM 再次调用 submit_program(source=修正版)
```

整个 loop 的状态非常明确。

甚至你可以要求：

> 当前 turn 只能通过 `submit_program` 提交候选程序。

这样一次 repair 就天然对应一次 candidate program。

以后日志也很好分析：

```text
attempt 1
source hash
compiler diagnostics

attempt 2
source hash
diff
compiler diagnostics

attempt 3
success
```

这对你现在正在做的语言实验特别有价值。

---

# 还有一个额外收益：你可以把不同“模型行为”隔离掉

目前 2.7% contamination 实际上混合了：

```text
语言生成错误
+
输出 framing 错误
```

例如：

````text
```dsl
return result
````

````

DSL 本身完全正确。

只是 transport 不符合预期。

如果把它计入：

```text
language conformance
````

其实污染了实验。

使用 tool envelope 之后，你可以真正区分：

```text
transport_success
syntax_success
compile_success
task_correctness
```

比如：

```text
transport_success = 100%
compile_success   = 97%
```

你才知道 3% 是语言问题。

而不是 Markdown 问题。

# 不过我不建议 Tool Schema 变复杂

这里有个陷阱。

千万不要重新做成：

```json
{
  "nodes": [
    {
      "type": "map",
      "source": "...",
      "tool": "..."
    }
  ]
}
```

那就绕回最初的问题了。

应该只做一个极薄的 envelope：

```text
submit_program(
    source: string
)
```

最多再加：

```text
language_version
```

例如：

```json
{
  "source": "...",
  "language_version": "0.3"
}
```

甚至第一版连 version 都不用模型填，Harness 自己决定。

**结构化约束只负责包裹，不负责表达程序。**

---

# 我甚至会再进一步：不要叫 tool 名字太业务化

比如：

```text
compile_dsl
```

其实不够准确，因为 compile 是 Harness 做的，不是模型做的。

可以叫：

```text
submit_program
```

或者：

```text
emit_program
```

语义非常清楚：

> 模型负责提交 source，Harness 决定 compile / validate / execute。

这个边界很好。

# 你可以专门做一个很小的 R3.5 / Transport 实验

这其实值得测，不要直接凭感觉改。

同样的 R3 最佳语言 B：

```text
_.field
```

比较两臂。

### A：raw text

要求：

```text
只输出 DSL，不要 Markdown
```

然后统计：

```text
markdown contamination
leading prose
trailing prose
empty output
extract failure
```

### B：tool envelope

唯一允许：

```text
submit_program(source=...)
```

统计：

```text
tool call success
missing source
invalid source type
compile success
```

然后关键指标：

```text
transport conformance
```

如果现在 raw 是：

```text
97.3%
```

而 tool envelope：

```text
99.9% / 100%
```

那这就是很直接的工程决策。

还可以顺便测：

```text
token overhead
latency overhead
repair success
```

因为 tool calling 可能多一点 schema prompt token，但如果换来接近零 framing error，通常很值。

# 我认为这个设计还解决一个产品化问题

实际 Agent Harness 不可能长期相信：

> “模型说自己这里只输出代码，所以我们 regex 一下就行。”

生产系统更希望有明确的 protocol boundary：

```text
Natural-language response
和
Executable artifact
```

必须是两个不同 channel。

你现在实际上可以把：

```text
assistant text
```

当成给人的输出，

把：

```text
submit_program
```

当成给机器的输出。

以后甚至一个模型 turn 同时可以：

```text
assistant:
“我会先检查仓库，然后分析候选。”

tool:
submit_program(source="...")
```

Harness 只执行 tool payload。

不会把人类解释和机器程序混起来。

---

## 我甚至认为这和你整个项目的哲学是一致的

你一开始做 DSL，就是因为不希望：

```text
LLM 自己负责底层结构正确性
```

所以你加了 compiler boundary。

现在这个 2.7% contamination 其实是同一种问题的上一层：

```text
你仍然让 LLM 自己负责“把程序正确包在文本里”
```

那就再把这一层也确定化。

于是整体变成：

```text
               自由语义
                   ↓
                  LLM
                   ↓
          structured submission
          submit_program(source)
                   ↓
            deterministic parser
                   ↓
            semantic compiler
                   ↓
              ExecutionIR
                   ↓
             deterministic runtime
```

这条链很完整。

我的建议因此很明确：

> **是的，应该用 tool calling 包装程序提交，但 tool calling 只做可靠 transport，不承担程序本身的结构表达。**

这样既保留了 DSL 带来的高密度、可编程表达，又利用现有 LLM 在结构化工具调用上的可靠 framing，避免把 Markdown stripping 这种启发式逻辑带进最终架构。

而且这件事值得作为一个单独实验记录下来，因为你现在实际上已经开始区分两个完全不同的问题：

> **语言是否 model-native？**
>
> **程序提交协议是否 production-grade？**

这两个问题最好不要再混在一个“生成成功率”里。

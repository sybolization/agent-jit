对，这时候最合理的目标已经不是“做一个 Workflow DSL”，而是先做一个 **Agent Execution DSL demo**，验证一个更一般的命题：

> **LLM 能否用一门小语言描述异构计算图，由 Harness 统一调度程序、工具、Agent 和控制流。**

你之前的多智能体调度其实已经有 runtime 了，只是缺了合适的 source language。JSON 当时相当于直接让模型手写 IR，所以表达力和可组合性都会受限。

我会刻意让第一版 demo **不绑定 workflow 语义**，而围绕“异构节点 + 数据依赖”设计。

### 核心抽象

图上的节点先只分四种：

```text
tool        外部工具/API
agent       LLM / sub-agent
compute     确定性程序
control     branch / parallel / retry / join
```

于是可以自然表达：

```agent
let issues = tool.github.search_issues(
  repo: "acme/core",
  state: "open"
)

let classified = parallel issues |> map(issue => {
  agent classifier {
    task: "classify issue"
    input: issue
  }
})

let bugs = classified |> filter(.type == "bug")

let stats = compute {
  total: len(bugs)
  critical: count(bugs, .severity == "critical")
}

let analysis = agent analyst {
  input: {
    issues: bugs
    stats: stats
  }
  task: "analyze the most important engineering problems"
}

return analysis
```

这里已经同时出现：

```text
Tool → Agent → Program → Agent
```

但对 LLM 来说，它只是在写一个小程序。

---

### `agent` 最好是一等 primitive

这是和普通 workflow DSL 最不同的地方。

不要把 Agent 特殊处理成 Harness 外层逻辑，而应该让它和 tool 一样出现在程序里：

```agent
let research = agent researcher {
  task: "research market"
  input: topic
}

let numbers = tool.finance.lookup(research.companies)

let valuation = compute {
  ...
}

let verdict = agent investor {
  input: {
    research,
    numbers,
    valuation
  }
}

return verdict
```

这样你之前的“多智能体调度”自然就变成了 DSL 的一个 use case，而不是单独一套系统。

甚至以后：

```text
Tool
Agent
Human
Workflow
Remote service
Local function
```

都可以统一成为：

```text
Executable<Input, Output>
```

再附带不同的 effect。

---

### `compute` 也很关键

如果没有这个，DSL 最终容易退化成：

> 更漂亮的 function calling。

真正把它变成“编程化 Agent”的是让 Harness 承担确定性计算：

```agent
let customers = tool.crm.list_customers()

let ids =
  customers
  |> filter(.revenue > 1_000_000)
  |> sort_by(.revenue desc)
  |> take(20)
  |> map(.id)

let records = parallel ids |> map(id =>
  tool.crm.get_customer(id)
)
```

这里：

* `filter`
* `sort`
* `take`
* `map`
* 数据搬运

全部不经过 LLM。

这才是在真正减少 agent loop。

## Demo 第一版我甚至只做 8 个 construct

不要先做复杂语言：

```text
let
call / tool
agent
compute
if
parallel
map
return
```

再加一个非常简单的数据表达体系：

```text
primitive
object
list
optional
reference
```

已经足够展示核心能力。

例如：

```agent
let candidates = parallel companies |> map(company => {
  let profile = tool.web.research(company)

  let score = agent scorer {
    input: profile
    task: "score this company from 0 to 100"
  }

  return {
    company,
    profile,
    score
  }
})

let best =
  candidates
  |> filter(.score > 80)
  |> sort_by(.score desc)
  |> take(5)

return best
```

Harness 编译成：

```text
                ┌─ research(A) ─ scorer(A) ─┐
companies ──────┼─ research(B) ─ scorer(B) ─┼─ join
                └─ research(C) ─ scorer(C) ─┘
                                              ↓
                                            filter
                                              ↓
                                             sort
                                              ↓
                                             take
```

这就是你想展示的东西。

## 我会避免第一版出现 `workflow`

甚至语言中暂时都不需要 `workflow` 关键字。

因为一旦叫 workflow，别人很容易理解成 Zapier / Temporal / n8n 的另一套 DSL。

而你的 demo 真正应该让人看到：

> 这是 LLM 用来生成 **execution graph** 的语言。

workflow 只是：

```text
execution graph + persistence + triggers
```

Multi-agent system 是：

```text
execution graph + agent nodes
```

Tool orchestration 是：

```text
execution graph + tool nodes
```

Data pipeline 是：

```text
execution graph + compute nodes
```

Research agent 是：

```text
execution graph + tool + agent + parallel
```

这样你的语言抽象就不会被一开始的应用场景锁死。

## 一个我觉得很重要的设计：不要强迫源码长得像图

DSL 描述依赖，**编译器负责产生图**。

也就是说源码最好还是：

```agent
let a = ...
let b = f(a)
let c = g(a)
return h(b, c)
```

Harness 自动得出：

```text
    a
   / \
  b   c
   \ /
    h
```

不要让 LLM 写：

```agent
node A ...
node B ...
edge A -> B
edge A -> C
...
```

因为那又重新掉回了 JSON graph specification 的坑：LLM 得管理 node ID、edge、引用一致性。

**让变量引用本身定义边。**

这是 DSL 相较 JSON graph 最大的语义优势之一。

---

## 还有一个非常值得 demo 的能力：动态展开图

静态 DAG 不够代表 Agent。

例如：

```agent
let urls = tool.search(query)

let pages = parallel urls |> map(url =>
  tool.browser.fetch(url)
)
```

`urls` 在编译时不知道有几个。

所以实际上你不是简单编译成静态 DAG，而更像：

> **graph template / dynamic dataflow program**

运行到 `map` 时 Harness 才展开 N 个节点。

这会比传统 workflow DAG 更接近 Agent runtime 的真实需求。

以后甚至：

```agent
while agent.should_continue(state) {
    ...
}
```

就进入动态 control flow。

但这个可以第二阶段再做。

## Demo 最好直接设计三个案例

我会选彼此差异很大的案例，证明 DSL 不是 Workflow 专用。

**案例 A：工具编排**

```text
search → fetch × N → extract → rank
```

重点测 token / latency。

**案例 B：多智能体**

```text
researcher ─┐
critic ─────┼→ judge
engineer ───┘
```

重点展示 agent/program 在同一张图。

**案例 C：Agent + 程序混合计算**

```text
SQL → deterministic aggregation
           ↓
      agent interpretation
           ↓
      tool side effect
```

重点展示 **LLM 不再承担数据搬运和普通计算**。

如果三个都能用同一个 8～10 个 primitive 优雅表达，那么语言核心基本就找对了。

我甚至建议你第一版的定位用一句非常具体的话：

> **A small language for LLMs to program heterogeneous agent execution graphs.**

而不是 “agent workflow language”。

因为你现在真正重新抽象的东西，已经从 workflow 上升到了 **LLM ↔ runtime 的接口**。

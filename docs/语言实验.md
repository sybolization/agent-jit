对，这个发现比“模型第一次写错了”本身重要得多。它开始触及一个**语言设计是否顺着模型先验走**的问题。

我看了当前仓库可见的最新 README：现在已经有独立 `src/language`、`ExecutionIR`、runtime、mock GitHub tools 和 LLM experiment harness，实验会记录到 `logs/experiments/`；所以现在已经具备条件把这种生成偏差正式变成 benchmark，而不是只作为 anecdote。

你观察到的：

```text
tool="github.get_repository"
```

模型自发写成：

```text
tool=github.get_repository
```

我认为值得从三个层面理解。

### 1. 这可能不是“模型犯错”，而是 DSL 在逆着已有语义先验

对模型来说：

```python
github.get_repository
```

天然表示一个 **callable reference**。

而：

```python
"github.get_repository"
```

天然表示一个 **string literal**。

你现在实际上要求模型做的是：

```text
语义上：传递一个 callable
语法上：却把 callable 序列化成字符串
```

这就是一种 *stringly typed representation*。

所以模型把它改成裸标识符，很可能不是随机 syntax error，而是在恢复它训练中更熟悉的：

```python
map(items, some_function)
```

这种程序结构。

这和你当前 DSL 已经采用的另一个设计形成鲜明对比：README 明确规定“裸标识符就是引用，变量引用定义数据流边”。也就是说，对于数据你已经采用了 **reference semantics**，但对于 callable 仍然采用字符串编码。

这其实暴露出了语言里的一个不一致：

```text
source=repos
       ↑ real reference

tool="github.get_repository"
     ↑ encoded reference
```

我会认真考虑把它统一掉。

---

### 2. 但现在不要直接把整个 DSL Python 化

这个数据点目前只证明了一个很窄的假设：

> **Callable reference 用 Python-shaped symbol 表达，可能比 string literal 更符合模型先验。**

它还没有证明：

> lambda、comprehension、Python expression、if 全部都会更好。

因此我认为下一步非常适合做一个**极小的 controlled experiment**。

只修改一个变量。

当前版本：

```text
details = map(
    source=repos,
    tool="github.get_repository",
    key="full_name",
    concurrency=5
)
```

实验版本：

```text
details = map(
    source=repos,
    tool=github.get_repository,
    key="full_name",
    concurrency=5
)
```

其他语法完全不变。

Compiler AST 增加一个：

```ts
type CallableRef = {
  kind: "callable_ref"
  path: ["github", "get_repository"]
}
```

然后编译成同一个 ExecutionIR：

```text
github.get_repository
```

**不要让 Runtime 行为发生任何变化。**

这样你测到的就是纯粹的：

> quoted callable vs symbolic callable

而不是“旧 DSL vs 一整套新 Python DSL”。

---

## 这个实验我甚至认为应该排在完整 Python-shaped A/B 之前

可以做三臂：

| Arm | 表达                                       |
| --- | ---------------------------------------- |
| A   | `tool="github.get_repository"`，zero-shot |
| B   | `tool="github.get_repository"`，few-shot  |
| C   | `tool=github.get_repository`，zero-shot   |

重点不是只测最终成功率。

一定保留 **first generation**，记录：

```text
first-attempt conformance
repair count
output tokens
prompt tokens
syntax errors
semantic errors
callable representation errors
```

因为现在这个现象最有意思的地方就是：

> few-shot 能把模型“纠正”回来，但纠正模型本身也是有成本的。

如果 C 在 zero-shot 下天然达到 B 的效果，那么 DSL 就可以删除一部分 instructional prompt。

最终你可能发现：

```text
旧 DSL:
语言更简单
但 prompt 必须不断告诉模型
“tool 必须写成字符串”

Python-shaped DSL:
parser 稍复杂一点
但 prompt 可以更短
模型第一次就写对
```

对于 LLM-first language，后者完全可能是更优 trade-off。

# 我建议开始建立一个“模型摩擦指标”

你们以前主要测：

```text
tokens
latency
conformance
transaction failure
```

现在可以增加一个很有意思的维度：

> **Model-language friction**

也就是模型会反复自然生成、但语言拒绝的 pattern。

例如日志中统计：

```text
bare_callable_reference       17
python_boolean_True            8
attribute_expression           6
lambda_expression              4
list_comprehension             3
positional_arguments           2
```

然后判断每一种 friction：

```text
模型偶发错误
    ↓
few-shot 修

还是

模型稳定的结构性先验
    ↓
考虑修改语言
```

这其实是一种非常适合 LLM DSL 的语言演化方法：

> **不要凭人类审美设计语法，让模型生成分布反过来参与语言设计。**

---

# 特别是不要过早把这种错误自动修复掉

例如 compiler 完全可以偷偷把：

```text
tool=github.get_repository
```

normalize 成：

```text
tool="github.get_repository"
```

产品上这很实用。

但**实验阶段先别这么干**。

否则你会失去非常珍贵的数据：

> 模型到底想写什么？

现在正处于语言成型阶段，compiler rejection 本身就是探针。

我甚至会在 diagnostic 中单独分类：

```text
EXPECTED_STRING_GOT_CALLABLE_REF
```

而不是笼统归类成：

```text
TYPE_MISMATCH
```

以后跑 100 个任务，你就能看到这种倾向究竟是不是稳定现象。

---

# 更深一层：这可能意味着 `map` 当前的抽象也值得调整

现在类似：

```text
map(
    source=repos,
    tool="github.get_repository",
    key="full_name"
)
```

其实把一个很自然的程序：

```python
github.get_repository(repo.full_name)
```

拆成了三个 DSL metadata：

```text
source
tool
key
```

这是 compiler-friendly，但不一定是 model-friendly。

模型真正习惯的是：

```python
details = map(
    repos,
    lambda repo: github.get_repository(repo.full_name)
)
```

或者：

```python
details = [
    github.get_repository(repo.full_name)
    for repo in repos
]
```

我现在不会马上实现它，但你已经第一次拿到了支持这个方向的真实 evidence。

可以把演化路径做得非常克制：

```text
P0
tool="github.get_repository"

↓

P1
tool=github.get_repository

↓

P2
map(repos, github.get_repository, key="full_name")

↓

P3
map(repos, lambda repo: github.get_repository(repo.full_name))

↓

P4
受限 comprehension
```

每升一级都做 A/B。

如果 P1 已经解决绝大部分 friction，那完全没有必要做 P3/P4。

## 最终甚至可以形成一条很有意思的语言设计原则

不是：

> “我们的 DSL 应该像 Python。”

而是：

> **Where Python syntax already expresses the desired execution semantics unambiguously, reuse the model's Python prior. Where Python semantics would destroy static analyzability, stop.**

中文就是：

> **Python 的形，Agent Runtime 的义。**

例如可以借：

```python
x = ...
foo.bar(...)
x.field
True
False
[1, 2, 3]
lambda x: ...
```

但不借：

```python
exec
import
reflection
mutation
arbitrary while
dynamic dispatch
exceptions as control flow
arbitrary user functions
```

这个边界比“Python subset”这个说法更精确。

---

所以我认为这次最值得做的不是立刻修改 DSL，而是把这个现象**正式升级成实验假设 H4**：

> **H4：当 Agent DSL 的表面语法与模型已有的程序语言先验一致时，可以减少 instruction burden 和 repair rounds，而不牺牲 ExecutionIR 的静态可分析性。**

你之前已经有了关于 **DSL vs JSON** 的系统效率证据；现在开始出现第二条研究线：

> **什么样的 DSL，才真正是 model-native 的？**

这条线可能最终比“语法像不像 Python”更有研究价值。
也就是我们要开始语言实验？

是的，但我会把它定义成受控的语言实验，不是现在就开始“大规模设计新语法”。

你们已经有了第一个很好的自然实验信号：模型自发把

tool="github.get_repository"

写成

tool=github.get_repository

这说明现在最值得做的是验证：

哪些语法形状更贴合模型先验，同时仍然保持静态可分析、可编译、可调度。

第一轮实验不要改太多，只测 callable reference：

A: tool="github.get_repository"
B: tool="github.get_repository" + few-shot
C: tool=github.get_repository

完全相同的任务、相同 IR、相同 runtime，只比较：

first-attempt conformance
repair 次数
output tokens
prompt/catalog tokens
syntax / semantic error 分布
最终成功率

如果 C 在 zero-shot 下接近甚至超过 B，那就说明“Python-shaped symbol reference”不是审美偏好，而是有实证价值的语言设计。

然后第二轮再逐步测：

字符串 where
vs
Python-like expression

key="full_name"
vs
repo.full_name

map(source=..., tool=..., key=...)
vs
map(repos, lambda repo: ...)

每次只改一个维度。

我会把整个研究路线概括成：

先发现模型摩擦 → 提出语法假设 → A/B → 只有显著改善才进入语言。

这样你们不是凭感觉“造 Python-like DSL”，而是在做一种 model-driven language design。

现在确实到了开始语言实验的阶段。并且我认为这会成为这个独立项目最有价值的一条主线之一。

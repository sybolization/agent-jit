可以，而且看过你现在的仓库后，我觉得**不应该推倒重来**。你现在已经有一个相当好的 seed：现有 DSL 是 `<name> = <callee>(...)`，变量引用自然定义数据流边；编译器已经有 tokenizer、递归下降 parser、批量诊断、类型/参数检查；目录也能自动渲染成给 LLM 的调用签名。仓库自己也已经明确写出了向 `tool / agent / compute / control` 泛化的方向。([GitHub][1])

我会把第一版 GitHub demo 定义成一个非常具体的目标：

> **用户用自然语言提出一个 GitHub 分析任务 → LLM 一次生成 DSL program → 编译器生成 Execution Plan → Harness 自动并行调用多个 GitHub API、做确定性数据加工 → 最后只把必要的数据交给 Agent 做语义判断。**

而不是做“GitHub Agent”。

## 第一版先别改语言表面语法

这是我现在最强烈的建议。

你现有语言：

```text
name = callee(key=value, ...)
```

已经足够做第一版 Agent Execution DSL。变量引用形成边的机制也是现成的。([GitHub][1])

**先不要加入：**

```text
|>
lambda
for
{}
while
复杂 expression
```

否则项目会迅速变成 parser 项目。

第一版可以写成这样：

```agent
repos = github.search_repositories(
  query="agent framework language:typescript",
  limit=10
)

details = map(
  source=repos,
  tool="github.get_repository",
  key="full_name",
  concurrency=5
)

active = filter(
  source=details,
  where="archived == false && stars > 100"
)

ranked = agent.rank(
  source=active,
  task="Rank the most actively maintained agent frameworks"
)

return(value=ranked)
```

你甚至可以继续要求“一条 statement 一行”，保持现有 parser 几乎不动。

这里已经出现了四类节点：

```text
github.search_repositories    tool
map                           control
filter                        compute
agent.rank                    agent
return                        control
```

**这就已经证明了 heterogeneous execution graph。**

# 第一步：先定义新的 IR，而不是继续设计语法

你现在的编译目标是 `SemanticCanvasGraphV1`，而且 `compileCanvasDsl()` 现在直接构建 workflow node。([GitHub][2])

新项目第一件事应该是把这一层切开：

```text
Source
  ↓
Parser
  ↓
AST
  ↓
Execution IR
  ↓
Runtime
```

我会定义一个非常小的：

```ts
type ExecutionNode =
  | ToolNode
  | MapNode
  | ComputeNode
  | AgentNode
  | ReturnNode
```

例如：

```ts
type ToolNode = {
  id: string
  kind: "tool"
  tool: string
  args: Record<string, ValueExpr>
}

type MapNode = {
  id: string
  kind: "map"
  source: Ref
  tool: string
  key: string
  concurrency: number
}

type AgentNode = {
  id: string
  kind: "agent"
  input: Ref
  task: string
}
```

注意这里一个重要选择：

**IR 可以是 JSON。**

完全没问题。

你的论点不是“JSON 不该存在”，而是：

> **LLM 不应该直接书写 Runtime IR。**

DSL 是 authoring surface，JSON/对象结构继续作为 compiler IR。

这延续了你现在项目里已经验证过的设计：作者面用 DSL，执行物保持确定性结构。([GitHub][1])

---

# 第二步：GitHub 只实现 4 个 Tool

不要一上来包装几十个 API。

我建议：

```text
github.search_repositories
github.get_repository
github.get_languages
github.list_contributors
```

最多再加：

```text
github.list_commits
```

GitHub REST 本身提供 repository、contributors、languages 等正式 endpoint。([GitHub Docs][3])

Tool contract 可以统一成：

```ts
interface Tool<I, O> {
  name: string
  inputSchema: Schema<I>
  outputSchema: Schema<O>

  execute(input: I, ctx: ExecutionContext): Promise<O>
}
```

然后：

```ts
registry.register({
  name: "github.get_repository",
  inputSchema: ...,
  outputSchema: ...,
  execute: ...
})
```

这会成为以后任何 tool adapter 的统一接口。

# 第三步：把你现有 Catalog 机制泛化

这部分我认为几乎可以直接继承。

你现在已经有：

```ts
renderWorkflowDslCatalog(workflowTools)
```

它会从 runtime 的 tool declaration 自动生成给 LLM 的 DSL 签名，而且明确告诉模型参数名、类型、required 等信息。([GitHub][4])

新版本改成：

```ts
renderToolCatalog(registry)
```

生成：

```text
github.search_repositories(
  query=string*,
  limit=integer
) -> list<RepositorySummary>

github.get_repository(
  full_name=string*
) -> Repository

github.get_languages(
  full_name=string*
) -> object
```

这一步非常重要，因为你之前已经踩过：

> LLM 幻觉合理参数名。

而 `unknown_parameter + config_type_mismatch` 正是你们从 60% conformance 修到 100% 的关键之一。([GitHub][1])

新项目一定要继承这个经验。

# 第四步：Runtime 先做最小调度器

这一块才是新项目真正需要写的东西。

第一版 runtime 不需要 Temporal 那样复杂。

只做：

```text
Value Store
Dependency Resolver
Ready Queue
Concurrency Limiter
Node Executor
Trace Collector
```

普通 ToolNode：

```text
inputs ready
    ↓
execute tool
    ↓
store output
    ↓
unlock dependents
```

真正有意思的是 `map`。

例如：

```agent
repos = github.search_repositories(...)

details = map(
  source=repos,
  tool="github.get_repository",
  key="full_name",
  concurrency=5
)
```

编译期图是：

```text
search
  ↓
 map
```

运行到 `map` 后：

```text
               ┌ get_repo(A) ┐
               ├ get_repo(B) ┤
search → map → ├ get_repo(C) ┤ → join
               ├ get_repo(D) ┤
               └ get_repo(E) ┘
```

这就是你之前说的：

> Agent 与程序同时在一张图调度。

而且它已经不再是静态 workflow DAG，而是 **dynamic graph expansion**。

这是 demo 最值得展示的技术点之一。

---

# 第五步：`compute` 第一版不要允许任意 JS

我不建议：

```agent
compute {
   任意代码
}
```

那会立刻带来 sandbox、安全、可复现性、hash、side effect 等一整套问题。

先提供 closed operators：

```text
filter
sort
take
project
count
group
```

例如：

```agent
popular = filter(
  source=details,
  where="stars >= 500"
)

recent = sort(
  source=popular,
  by="pushed_at",
  order="desc"
)

top = take(
  source=recent,
  count=5
)
```

这些仍然是程序计算，但 Harness 可以百分之百确定执行。

以后再考虑 expression VM。

---

# 第六步：最后才加入 `agent`

一旦 Tool → Map → Compute 跑起来，加入 agent node 实际上很简单：

```agent
analysis = agent(
  source=top,
  instruction="Compare these repositories and explain which appears healthiest"
)
```

Runtime 眼中：

```text
ToolNode    → GitHub adapter
ComputeNode → local runtime
AgentNode   → model adapter
```

因此你会得到第一张真正的 heterogeneous graph：

```text
GitHub search
      ↓
     map
  ↙ ↓ ↓ ↓ ↘
repo repo repo repo
  ↘ ↓ ↓ ↓ ↙
     join
      ↓
    filter
      ↓
     sort
      ↓
     take
      ↓
    Agent
      ↓
    return
```

而 Agent 只看到 `take` 后的少量结果。

**这正是 demo 的核心。**

# 我建议的第一个真实任务

不要做模糊的“研究 AI 项目”。

用一个 deterministic enough 的任务：

> Find active open-source TypeScript agent frameworks on GitHub. Inspect the top 10 repositories, filter out archived or low-activity projects, and identify the 3 most interesting projects based on activity, contributors, stars, and language composition.

它会要求：

```text
1 × search
10 × get_repository
10 × get_languages
10 × contributors
若干 deterministic operations
1 × LLM analysis
```

传统 Agent：

```text
LLM
→ search
→ LLM
→ repo
→ LLM
→ repo
→ LLM
...
```

你的 DSL：

```text
LLM
→ program
→ compiler
→ runtime executes ~31 calls
→ LLM analyzes compact final data
```

差异会非常清楚。

# GitHub 接入我会分两个阶段

### Demo V0：直接用 `gh api`

你已经有 GitHub 账号，所以本地先：

```bash
gh auth login
```

GitHub 官方 CLI 就支持这种认证方式。([GitHub Docs][5])

Tool adapter 内部甚至可以先：

```text
exec("gh api ...")
```

优点是：

* 不写 OAuth
* 不处理 token UI
* 马上能工作

### Demo V1：改成 REST adapter

等 DSL/runtime 跑通以后，再从 subprocess 换成：

```text
fetch(api.github.com/...)
```

Runtime 自己读取 token。

这样长期架构更干净。

而且 Runtime 最好自己做 concurrency limit；GitHub REST 有 primary/secondary rate limits，搜索 endpoint 还有单独、更严格的限制。([GitHub Docs][6])
